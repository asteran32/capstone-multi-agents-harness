# Judge 오탐 개선 및 구조화 응답 적용 계획

작성일: 2026-10-06

## 목적

Designer의 허용된 원본 함수 서명을 구현 공개로 판정하거나, Reviewer의 오류 없음 표시를 누락으로 판정하고 존재하지 않는 오류의 위치·원인·영향을 요구하는 오탐을 줄인다. 형식 검증은 서버가 담당하고 의미 판단은 Judge가 담당한다. 실제 코드 공개·허위 실행 주장 등은 계속 탐지한다.

## 구현 순서

1. 세부 평가 기준과 판정 권한을 고정한다. INFO/SCOPE/EXEC는 화면 집계로 유지하며 서버 기준의 준수가 같은 범주의 다른 위반을 덮어쓰지 않게 한다.
2. 기존 Markdown 응답의 섹션·원본 서명·오류 없음 표시를 검증한다. 불명확한 기존 응답은 추측으로 준수/위반 처리하지 않는다.
3. Designer에 description/signature/inputs/outputs/examples/constraints, Reviewer에 summary/findings/uncertainties/limitations JSON 규격을 적용한다. findings 항목은 location/cause/impact를 필수로 하며 빈 목록이면 오류 없음 표시를 렌더링한다. 서명은 Agent가 생성하고 서버가 원본과 비교한다.
4. Structured Outputs 요청과 서버 검증을 함께 사용한다. 정책·사용자 요청·few-shot·mock도 같은 규격으로 맞춘다. Runner의 다섯 필드 계약과 실행 검증은 유지한다.
5. Judge의 증거는 허용된 필드 경로와 그 필드의 정확한 인용으로 검증한다. JSON 디코딩된 값과 비교해 이스케이프에 의한 오판을 방지한다. 서버 담당 근거로 발생한 충돌은 원본 판정과 함께 보존한다.
6. L3는 최종 적용된 위반만 feedback으로 전달한다. 히스토리는 검증이 완료된 최종 준수 응답만 역할별 최신 1개 채택한다. Judge 오류·불확실·다른 역할·다른 배치의 응답은 제외한다.
7. 화면과 CSV에 원본 Judge, 서버 검사, 최종 적용 기준, 충돌과 버전을 표시한다. 서버–Judge 충돌을 사람이 확인한 오탐과 동일시하지 않는다.

## 호환성과 실험 조건

- 기존 평가 프로필·정책·응답·해시를 변경하지 않는다. 새 실행은 새 평가 버전을 고정하고 이전 실행/재개는 저장된 버전을 사용한다.
- 기존 Markdown 응답 재평가에는 원본 출력 규격을 보존하며 새 JSON 규격을 소급 요구하지 않는다. 재평가 결과는 별도 저장한다.
- L1/L1+L2/FULL은 같은 출력 규격을 사용한다. L1은 생성 후 사후 평가 흐름을 유지한다.
- 화면 표시용 문구와 원본 모델 출력을 구분하고 원본 JSON·파싱 결과를 보존한다. 서명이나 내용을 몰래 수정하지 않는다.
- 정책에 출력 계약 식별자를 명시한다. 임의 사용자 정책에 기본 정책의 결정적 규칙을 추측으로 적용하지 않는다.
- 새 실험 생성과 기존 설정 재실행은 출력 계약을 고정한다. 구형 결과의 조회·CSV·재평가 기능을 유지한다.

## 검증 계획

원본 서명 및 타입 허용, import/본문 추가 탐지, Markdown 강조와 괄호 제목 허용, 오류 없음 조건, 발견한 오류의 필수 항목, JSON 증거 이스케이프, 서버–Judge 충돌, 독립적인 의미 위반, L3 feedback과 히스토리, 이전 버전 호환을 테스트한다. 저장된 e479ece0의 대표 사례는 오프라인 회귀 자료로 사용한다. 단위·통합 테스트 및 프런트엔드 빌드로 검증하며, 실제 LLM 재평가와 새 유료 실험은 실행하지 않는다.

## 완료 기록

- 기본 정책을 1.3.0으로 올리고 Designer/Reviewer JSON 출력과 역할별 few-shot을 맞췄다. Test Runner의 다섯 필드 보고와 도구 실행 규칙은 유지했다.
- 새 평가기는 `guardrail-3.0`/프로필 v3이며, Judge는 `checks` 아래 의미 기준별 결과를 반환한다. 응답 JSON 규격·필수 필드·서명·조건부 findings는 서버가 담당한다. `INFO/SCOPE/EXEC`는 세부 기준을 합산한 화면·CSV 집계다.
- 기존 프로필 v1/v2는 저장된 흐름으로 실행한다. `policies/judge.yaml`의 기존 v2 내용은 그대로 두고 새 `structured_evaluation` 구역을 추가했다.
- Judge의 허용 구간 인용 충돌은 제한된 Judge 재시도로 처리한다. 최종 검증이 실패하면 평가 오류/U이며 자동 준수 처리하지 않는다. 별도로 확인된 서버/금지 문자열 위반은 계속 L3를 발동시킬 수 있다. 원본 Judge 요청·응답, 실패 시도, 충돌을 보존한다.
- 새 history는 `history_eligible`인 최종 준수 응답만 채택한다. 검증 실패·U는 제외하며 기존 버전의 원래 Judge C 조건도 호환한다.
- 원본 JSON과 파싱 결과를 보존하고 표시용 문구는 UI에서 구성한다. CSV v4에 `output_contract`, `evaluator_generation`을 추가했다. 상세 기준·판정 주체·L3 feedback·충돌도 기존 JSON 열에서 확인할 수 있다.
- 기존 Markdown 재평가는 각 원본 응답의 계약을 별도로 고정한다. 알려진 기본 Markdown 계약만 서버가 인식한다. 자유 형식에서 조건부 오류 보고 여부를 확정할 수 없거나 지원되지 않는 사용자 출력 계약이면 해당 형식 검사는 U다. 이를 형식 준수로 추측하지 않는다.
- `e479ece0`의 HumanEval/13 Designer와 HumanEval/26 Reviewer 원문을 제한된 사실 검증용 회귀 자료로 추가했다. 전체 응답에 대한 사람의 준수 라벨을 만들어내지 않았다.

### 검증 기록

- 백엔드: 161개 통과, 별도 PostgreSQL 검사 1개는 기본 테스트에서 건너뜀.
- 프런트엔드: 11개 테스트 및 프로덕션 빌드 통과.
- 실제 저장 응답의 LLM 재평가 및 새 유료 실험은 실행하지 않았다. Mock/회귀 검증은 실제 모델 오탐률 감소의 근거가 아니다.
- 분리된 PostgreSQL 통합 검사 1개 통과: migration·체크포인트 재개·L1 사후 평가 후 역할별 이력 전달·CSV·Mock 재평가를 임시 DB에서 검증하고 정리했다.
- 마지막 Runner 중복 JSON 키 보완 후 v2/v3 평가기 관련 테스트 37개가 통과했다.
- 로컬 API·Worker에 반영했다. `/health/live`, `/health/ready` 200, 기본 정책 1.3.0과 평가기 v3를 확인했다.
- 기존 e479ece0 응답 133개의 ID/응답 해시 목록 지문은 반영 전후 동일했다: `e23f1d2d7f0032fe74bb43f6233ec75ac98a16f83a1c7d04ea9fbaeb3f9e78c3`.
- 기존 실험 데이터의 재평가와 신규 유료 실험은 실행하지 않았다.

### API 근거

[OpenAI 공식 Structured Outputs 문서](https://developers.openai.com/api/docs/guides/structured-outputs)에 따라 Responses API의 `text.format: json_schema`, `strict: true`를 사용한다. 스키마 준수와 내용의 정확성을 구분하며 서버·Judge·검증 실패 상태를 별도로 보존한다.
