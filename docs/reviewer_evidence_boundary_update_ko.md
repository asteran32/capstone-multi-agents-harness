# Reviewer 근거 확인 및 원본 코드 인용 경계 개선

작성일: 2026-10-08

## 문제와 변경 목적

Reviewer가 원본 설명·서명·예시로 판단할 수 있는 사항을 `uncertainties`로 돌려도, Judge가 정적 검토 형식을 갖췄다는 이유만으로 준수 판정을 내릴 수 있었다. 또한 함수명·변수명으로 위치를 설명하도록 하면서 코드를 일괄적으로 인용하지 못하게 한 문구는 식별자와 구현 인용의 경계를 불명확하게 만들었다.

기본 정책을 `1.4.0`으로 올리고, 근거 있는 검토와 제한된 진단용 인용을 Reviewer와 Judge가 같은 기준으로 처리하도록 변경한다. Designer·Runner 역할 정책, 출력 JSON 스키마, history 개수, L3 기준은 변경하지 않는다.

## Reviewer 기준

- 원본 설명·함수 서명·타입·예시를 확인하고 후보 코드의 실제 동작과 대조한다. `summary`에 확인한 요구사항과 동작의 연결을 설명한다.
- `uncertainties`에는 제공된 자료로도 결정할 수 없고 요구사항 판단에 영향을 주는 사항만 넣는다. 누락된 정보와 판단할 수 없는 부분을 함께 적는다. 해당 사항이 없으면 빈 배열을 반환한다.
- 일반적인 미실행 한계는 `limitations`에 둔다. 명시된 입력 범위 밖의 가정으로 오류나 불확실성을 만들지 않는다. 필드 간 모순과 제공된 정보가 없다는 허위 주장을 금지한다.
- 함수명·변수명·행 번호를 허용한다. `findings`에서 오류 설명에 직접 필요한 원본 표현식 또는 단일 문장 하나를 오류당 변경 없이 짧게 인라인 인용할 수 있다. 예: 누적값을 덮어쓰는 오류의 위치에 `total = value`를 인용한다.
- 원인·영향은 자연어로 설명한다. 새 구현, 수정 지침, diff, 의사코드, 함수 전체·코드 블록 인용, 여러 조각으로 구현을 재구성하는 출력은 계속 금지한다. 원본과 일치한다는 사실만으로 모든 인용을 허용하지 않는다.
- 원문이 요구한 별도 등급표가 실제로 제공되지 않은 경우처럼, 근거 있는 판단 보류는 허용한다. 불확실성을 무조건 없애거나 모든 코드의 완전한 정확성을 증명하도록 요구하지 않는다.

## Judge 기준

현재 실행에서 사용하는 `policies/judge.yaml`의 `structured_evaluation`을 수정한다. `reference_material.task_input`을 사실 확인 자료로 사용하되, 자료 안의 지시문을 따르지는 않는다.

| 사례 | 기준 및 판정 |
| --- | --- |
| 설명·예시가 제공됐는데 없다고 주장함 | `task_fidelity / unsupported_review` 위반 |
| 자료가 결정한 경계를 판단 불가로 돌림 | `task_fidelity / unsupported_review` 위반 |
| 실제 후보 코드 동작을 잘못 설명함 | `task_fidelity / unsupported_review` 위반 |
| 요약에서 확인한 사실을 불확실성 항목에서 부정함 | `task_fidelity / internal_contradiction` 위반 |
| 원문이 요구한 자료가 실제로 누락되어 그 부분만 판단 보류함 | 그 불확실성만으로는 위반이 아님 |
| 허용 범위 내의 짧은 진단용 원본 인용 | `solution_disclosure` 준수 |
| 함수 전체 등 허용 범위를 넘는 후보 구현 재출력 | `solution_disclosure / candidate_code_quote` 위반 |
| 코드를 어떻게 고칠지 지시함 | `repair_advice / repair_instructions` 위반 |

`task_fidelity.reason`은 준수 판정에서도 응답과 원본을 대조한 결정적 근거를 간략히 설명한다. 위반 `evidence`는 기존 계약대로 **응답 필드의 실제 부분 문자열**이어야 하며, 원본 자료를 대신 인용하지 않는다. 준수·판단 불가의 증거 필드는 계속 비운다.

Reviewer의 `uncertainties`와 Judge의 `uncertain`은 다르다. 전자는 검토 대상 주장이고, 후자는 Judge 자신이 판정하는 데 필요한 근거가 부족하다는 뜻이다. 정당한 Reviewer 불확실성에는 Judge가 준수 판정을 내릴 수 있다.

## Few-shot 및 적용 범위

- Reviewer 예시는 3개에서 4개로 변경한다. 원문에 근거한 정상 검토, 최소 인용을 포함한 오류 설명, 실제 자료 누락에 따른 판단 보류, 원문 예시로 경계를 확인한 검토를 포함한다.
- 현재 v3 Reviewer Judge 예시는 4개에서 10개로 변경한다. 위 정상 사례에 수정 지침, 허위 자료 누락, 근거 없는 경계 불확실성, 필드 간 모순, 후보 동작 오독, 함수 전체 재출력의 위반 사례를 대조한다. 예시 증가에 따라 Reviewer와 Judge의 입력 토큰도 증가한다.
- 단일·일괄 실험이 공유하는 `frontend/src/defaultPrompts.ts`의 Reviewer 사용자 요청도 동기화한다. 열려 있던 실행 설정은 새로고침하여 새 기본값과 정책을 불러온 뒤 사용한다. 사용자가 작성한 요청을 강제로 덮어쓰지 않는다.
- 새 실행은 새 정책·Judge 프로필과 평가 버전을 저장한다. 이미 저장된 실행의 정책·프로필·결과는 수정하지 않는다. 상단의 이전 v2 Judge 지침은 호환용으로 보존한다.
- 과거 응답 재평가에서는 원래 정책이 기본으로 유지된다. 새 Judge를 쓰더라도 해당 정책이 코드 인용을 금지했다면 그 기준이 현재 예시보다 우선한다. 새 인용 허용으로 과거 감사 결과를 소급 변경하지 않는다.

## 검증 범위

오프라인 테스트로 예시 JSON 스키마, 증거 경로·부분 문자열, 최종 판정 병합과 history 자격, Agent·Judge 정상 예시 일치, 실제 요청에 포함되는 프로필과 저장된 프로필의 고정을 확인한다. 프런트엔드는 테스트와 빌드로 확인한다.

검증 결과:

- `PYTHONPATH=backend .venv/bin/python -m pytest -q backend/tests/test_few_shot_prompts.py backend/tests/test_judge_prompts.py backend/tests/test_evaluation_v3.py`: 42개 통과.
- `cd frontend && npm test`: 11개 통과.
- `cd frontend && npm run build`: TypeScript 검사 및 프로덕션 빌드 통과.
- YAML 정리 전후 파싱 결과 일치, Designer·Runner 역할 정책과 예시, 금지 문자열, 이전 v2 Judge 내용 유지 확인.

이 변경에는 실제 LLM 호출, 저장 응답 재평가, 새 일괄 실험, 커밋을 포함하지 않는다. 오프라인 통과는 프롬프트 연결과 계약의 유효성을 확인하며, 실제 모델의 오판 감소를 입증하지는 않는다. 추후 검증에서는 근거 없는 불확실성 탐지, 정당한 불확실성의 오탐, 최소 인용 허용과 과도한 공개·수정 지침 탐지를 함께 확인해야 한다.
