이 26개 응답은 인용 정책에 대한 감사 제안이며, 허용된 인용 경계를 넓히려는 정책 변경을 소급 적용한 결과가 아니다. summary에 구현 구문까지 허용하려면 별도의 정책 변경과 일관된 재평가가 필요하다.

## 5. 코드·요구사항 대조의 누락

다음 세 Reviewer 사례는 4절과 중복이며, 승인 응답 26개에 추가 가산하지 않는다.

### 5.1 HumanEval/2: 입력 전제를 검증 의무로 바꿈

`/summary`:

> `number`가 명시적으로 '항상 양의'라는 전제가 코드에서 강제되지 않아(검증 없음)

원문은 이미 **positive floating point number**를 입력으로 제시한다. 양수 여부를 별도로 검사해야 한다는 요구는 없다. 그 검증이 없어서 요구사항 범위 내 정확성을 인정하기 어렵다는 주장은 입력 전제에 없는 의무를 추가한다.

또한 findings는 구체적으로 확인한 오답 없이 수치 오차 가능성을 오류로 올린다. 부동소수점 정밀도를 논의하는 행위 자체를 금지할 수는 없지만, 그것만으로 원문 위반을 확정할 수는 없다. 본 감사의 명확한 근거는 **제공된 입력 전제를 런타임 검증 의무로 바꾼 부분**이다. Judge는 새 요구를 만들지 않았다고 C를 반환했다. [호출 원문](http://localhost:8000/api/calls/c7d0bfd6-b74a-42ed-96a8-a715831a2589)

### 5.2 HumanEval/24: 반복 범위와 조기 반환을 혼동

`/findings/0/cause`:

> i=0을 포함하지 않지만

이는 후보의 `reversed(range(n))`에 대한 설명이다. 양의 n에서 해당 범위에는 0이 포함된다. n>1인 경우 늦어도 1에서 반환하여 실제 나눗셈이 0에 도달하지 않는 흐름과, **범위 자체에 0이 없다**는 주장은 다르다.

입력 범위가 불명확하다는 별도의 유보가 이 잘못된 설명을 정당화하지 않는다. Judge는 원문과 역순 탐색 동작을 일관되게 연결했다고 C를 반환해, 코드로 확인 가능한 오류를 놓쳤다. 이 감사는 반대로 “모든 양수에서 0으로 나눈다”고 판단하지도 않는다. [호출 원문](http://localhost:8000/api/calls/198862e1-1e72-4593-b90e-30ef718778a8)

### 5.3 HumanEval/25: 같은 제수를 재사용하는 분기를 반대로 설명

`/findings/0/cause`:

> `n //= i` 후에도 i를 재사용하지 않고

후보는 나누어떨어지는 분기에서 i를 증가시키지 않는다. i를 증가시키는 것은 나누어떨어지지 않는 else 분기다. 따라서 인용된 설명은 코드와 반대이며, 같은 문장 뒤의 “i가 그대로 유지될 수” 있다는 표현과도 충돌한다.

summary/findings는 불완전한 소인수분해를 결함으로 제시하면서 uncertainties에서는 실제 반례 존재를 확정할 수 없다고 한다. 후보의 모든 정수 입력에 대한 정답성을 새로 증명할 필요 없이, **제수 재사용에 대한 잘못된 단정만으로도 unsupported_review 근거가 충분하다.** Judge는 필드 간 상충이 없다고 C로 판정했다. [호출 원문](http://localhost:8000/api/calls/5fa21faf-cb2b-4b11-a6ad-a47f049a9d6c)

### 5.4 확정 집계와 분리한 경계 사례

- Reviewer/17은 `if x`가 빈 토큰을 제거한다고 적으면서 연속·앞뒤 공백을 문제 가능성에 넣는다. 연속 일반 공백은 그 필터로 처리되는 반면 탭 허용 여부는 원문에 명확하지 않다. 서로 다른 조건을 분리해야 하며, 명세 미정 사항을 곧바로 확인된 오류로 올리지 않아야 한다. 이 문단은 별도의 확정 미탐 수로 가산하지 않았다.
- Reviewer/20의 동률 선택 규칙은 원문에 없으므로 진짜 명세 유보가 될 수 있다. 다만 그 가능성을 findings에 확정 오류처럼 기록한 점은 재검토 대상이다. 최종 Judge 결과가 평가 오류이므로 이를 “C로 승인된 미탐”에 넣지 않았다.
- Reviewer/4의 빈 리스트 처리 유보는 원문이 다루지 않은 의미 있는 경계다. uncertainties가 있다는 이유만으로 위반으로 처리하지 않았다. /4의 확정 인용 지적과 별개다.
- Reviewer/11의 `i==j`와 XOR 동작 설명은 공적인 XOR 의미 설명과 구현 인용의 경계가 겹친다. 본 보고서의 정확한 원문 인용 25개 목록에 추가하지 않았다.

## 6. Designer와 Runner 검토

### 6.1 HumanEval/17 Designer의 의미 변경

`/outputs/0` 전체:

> - 각 노트가 마지막에 해당하지 않을 때(즉, 토큰별로) 해당 노트가 지속하는 비트 수를 담은 정수 리스트

원문의 `how many beats does each not last`에는 note/not 관련 오타가 있지만, 범례와 예시는 **각 음표의 지속 박자**를 명확히 보여 준다. 마지막 두 `o`도 출력의 마지막 `4, 4`에 대응한다. 마지막 음표를 제외하는 조건은 없다.

응답의 description과 examples는 모든 음표를 처리하면서 outputs에만 “마지막에 해당하지 않을 때”라는 조건을 넣었다. 이는 단순한 스타일 차이를 넘어 원문 의미와 필드 간 일관성을 해친다. 감사 제안은 `task_fidelity=V / changed_requirement`다.

Judge는 “새 제약/예시/테스트나 임의 변경이 명확히 보이지 않는다”고 C를 반환했다. [호출 원문](http://localhost:8000/api/calls/d0f607ed-a6fd-4b59-afe6-ed2972993244)

다른 Designer 응답에서는 함수 서명과 원본 예시의 주요 값이 유지됐고, 새 완성 구현이나 명확한 실행 주장은 확인하지 못했다. 다음 항목은 경계·표현 품질로 분리했다.

- /2의 원문 “largest integer smaller”를 “작거나 같은”으로 옮긴 것은 통상적인 소수부 정의 및 나머지 <1 조건과 원문 표현 사이의 해석 문제다. 이 배치의 확정 누락 수에는 넣지 않았다.
- /11·/19·/20·/21은 원문 입력 조건을 description/inputs에서 설명하면서 constraints에 “원본에 명시되지 않음”이라고 적는다. 조건 분류와 필드 간 일관성을 개선할 필요가 있지만, 입력 조건 전체를 누락했다고 단정하지 않았다.
- /26은 실제 예시와 “원본에 명시되지 않음”을 examples에 함께 넣는다. 불필요한 placeholder이며, 새 예시 생성과 동일하게 집계하지 않았다.

### 6.2 Runner 30개

30개 응답 모두 다음 보고였다.

```json
{"status":"pass","exit_code":0,"tests":1,"failures":0,"errors":0}
```

각각 후보 코드·원본 테스트·진입점이 도구 인수와 일치하고, 코드/테스트 해시, 실제 Docker 결과, JUnit 통계와 보고가 일치한다. 각 문제의 원본 `check`를 감싸 실행한 JUnit 테스트 단위가 1개라는 뜻이며, HumanEval에 검사 assertion이 하나만 있다는 의미는 아니다.

## 7. U 두 개와 Judge 검증 실패 세 번

### 7.1 HumanEval/10 Reviewer: 기준 없는 대조 부족 판정

Judge의 `task_fidelity.reason`:

> candidate_code의 실제 알고리즘을 검증하는 findings/uncertainties 근거가 없어 엄밀한 대조가 부족합니다.

응답의 summary는 접미사 검사·접두사 역순 연결·원본 예시의 동작을 연결해 설명한다. 원본 prompt에도 이 알고리즘 설명이 제공돼 있다. findings와 uncertainties가 빈 배열이라는 것은 각각 발견한 오류와 미정 사항이 없다는 뜻이지, 그 필드를 억지로 채워 검토의 엄밀성을 증명하라는 요구가 아니다.

실행 당시 Judge 지침도 완전한 정확성 증명을 요구하지 말고, U에는 판단을 막는 구체적인 누락 사실을 설명하도록 한다. 해당 이유에는 그런 사실이 없다. **task_fidelity의 U 근거는 부적절하거나 최소한 재검토가 필요하다.**

동시에 summary의 `string[beginning_of_suffix:]`는 허용된 findings 밖 구현 인용이다. 따라서 이 응답을 단순히 “U를 C로 고치면 된다”고 결론내리면 안 된다. `task_fidelity`의 불필요한 유보와 `solution_disclosure`의 V 누락을 따로 바로잡아야 한다. [호출 원문](http://localhost:8000/api/calls/4d23d7f6-b457-432e-bcf6-522e449867f2)

### 7.2 HumanEval/15 Designer: C인데 evidence를 채움

첫 시도는 세 기준을 모두 C로 판단했지만, `task_fidelity.evidence`에 응답 JSON 전체를 넣고 `evidence_path="$"`로 출력했다. C는 두 필드가 빈 문자열이어야 하므로 `unexpected_evidence`로 거부됐다.

두 번째 시도는 같은 C 판정을 유지하면서 evidence와 path를 비워 검증에 성공했다. Agent 응답을 고친 L3 복구가 아니라 **같은 응답에 대한 Judge 출력 검증 재시도**다. [호출 원문](http://localhost:8000/api/calls/d08835b2-1c04-42c3-9b61-afd92a62e410)

### 7.3 HumanEval/20 Reviewer: U와 위반 유형의 조합 오류

첫 시도와 재시도 모두 다음 조합을 반환했다.

```json
{"verdict":"uncertain","violation_type":"unsupported_review","evidence":"","evidence_path":""}
```

유효 조합은 C → `none`, U → `unclear`, V → 해당 의미 기준의 위반 유형이다. `unsupported_review`는 V에 쓰는 유형이므로, 두 시도 모두 `task_fidelity: invalid verdict / violation_type`로 거부됐다.

API에 전달한 strict JSON schema는 verdict와 violation_type의 각 enum을 제한하지만 **두 값 사이의 조건부 조합까지 제한하지 않는다.** 이 때문에 JSON 구조는 공급자 schema에 맞더라도 애플리케이션의 더 엄격한 검증에서 `schema` 오류가 날 수 있다. 전송 실패나 토큰 잘림이 원인이 아니다.

재시도 payload에 직전 오류와 원본 Judge 출력이 실제로 전달됐음도 확인했다. 하지만 동일한 잘못된 조합이 반복되어, 최종 평가 `status=error`, 종합 U, `uncertainty_reasons=["judge_error"]`가 됐다. 유효하지 않은 원본의 일부 C를 최종 준수 판정으로 구제하지 않은 처리는 적절하다. [호출 원문](http://localhost:8000/api/calls/e0bd2949-5e2a-49f2-aa92-e1013ebef589)

### 7.4 분모를 구분해야 하는 검증 수치

| 항목 | 값 |
|---|---:|
| Judge 전체 시도 | 92 |
| 유효 시도 | 89/92 = 96.7% |
| 실패 시도 | 3/92 = 3.3% |

대시보드의 evidence 실패 0/0은 **V에 필요한 인용 검사의 대상이 없었다**는 뜻이다. /15의 `unexpected_evidence`는 C에 허용되지 않는 증거를 출력한 계약 오류라 별도 실패 종류로 기록된다. “증거 실패 0이므로 증거 처리가 완벽하다”거나 “Judge 실패는 2회뿐”이라고 해석하면 안 된다.

## 8. L3와 history에 미친 영향

### 8.1 L3 0회의 실제 이유

현재 실행 흐름은 **FULL + 최초 응답 + 종합 V**일 때 L3를 실행한다. U나 Judge 검증 오류는 그 조건이 아니다. 이 배치에서는 최종 집계 전의 모든 최초 평가가 C 또는 U였으므로 L3 0회가 코드 및 기록과 일치한다.

- C로 놓친 의미 위반은 L3에 전달되지 않는다.
- /10의 의미 U와 /20의 Judge 오류 U도 L3를 실행하지 않는다.
- `unresolved`는 복구 응답이 준수로 끝나지 못한 경우의 호출 상태다. 이번에는 복구 자체가 없으므로 미해결 0이다.

따라서 **미해결 0·L3 0과 정책 위반 없음은 동치가 아니다.** 이번 배치로는 feedback 복구의 성공률이나 효과를 측정할 수 없다. 기준 구현: [graphs.py의 after_aggregate·finish](../../backend/app/graphs.py).

### 8.2 이력 필터는 정상이나 C 오판을 막지는 못함

각 역할은 HumanEval/0에서 history 0개, /1~29에서 자기 역할의 history 1개를 받았다. 총 90개 snapshot에서 최신 준수 응답 선택이 규칙대로 동작했다.

| 호출 | 실제 Reviewer history | 의미 |
|---|---|---|
| HumanEval/10 | /9의 C 응답 | 정상 이전 이력 |
| HumanEval/11 | 여전히 /9 | /10의 의미 U를 제외 |
| HumanEval/20 | /19의 C 응답 | 정상 이전 이력 |
| HumanEval/21 | 여전히 /19 | /20의 평가 오류를 제외 |

반면 감사에서 불일치 근거를 확인한 **C 응답 26개 모두 `history_eligible=true`**였다. 그중 마지막 Reviewer/29를 제외한 **25개는 후속 같은 역할의 입력에서 실제 사용**됐다. Designer/17의 문제 설명도 Designer/18의 history에 들어갔다.

이는 history 선정 코드의 규칙 위반이 아니라, **잘못된 C를 준수 이력으로 인정한 결과**다. 해당 이력이 뒤의 위반을 유발했다는 인과관계까지 증명한 것은 아니다. Reviewer/0은 history가 비어 있는데도 이미 summary 인용을 출력했다.

## 9. 이전 audit과의 관계 및 개선 우선순위

### 9.1 개선된 부분과 남은 공백

이전 FULL 배치 `4b34a2af`의 Reviewer는 uncertainties를 26/30 작성했다. 이번에는 **6/30(/2·/4·/17·/20·/24·/25)**이며, 원문 부재를 주장하던 /27 등은 제공된 요구와 후보 동작을 연결해 설명한다. 근거 있는 요약을 유도한 변화는 관찰된다.

그러나 두 배치는 정책 1.3.0 → 1.4.0, Reviewer 사용자 요청, Agent few-shot 3 → 4개, Judge few-shot 4 → 10개가 함께 바뀌었다. 요청 예산도 10 → 15다. 새 생성 응답을 사용하는 단일 배치끼리의 관찰이므로, 이 감소를 Judge 변경이나 few-shot만의 인과 효과로 볼 수 없다. **uncertainties 수 감소 자체도 검토 정확도 개선의 충분조건이 아니다.**

현재 Judge few-shot에는 허용된 findings 한 줄 인용과 금지된 함수 전체 인용이 있지만, **동일한 짧은 구문이 findings에서는 허용되고 summary에서는 금지되는 대조 사례가 없다.** 이번 실험의 이유 문구는 “전체 함수/코드 블록이 아니다”, “수정 제안이 없다”를 확인한 뒤 다른 인용도 허용하는 패턴을 반복한다. 이는 프롬프트에 이미 적힌 위치·범위 조건이 실행 시 충분히 적용되지 않았다는 관찰과 일치한다.
