### 4.4 불확실과 복구 결과

A의 최초 U 3건은 모두 Designer의 HumanEval/0, /15, /19였다. Judge는 각각 타입 표기·import 허용 여부, 제약 조건 추가 여부, 원본 함수 서명 일치 여부를 불확실 사유로 들었다. B에서는 같은 세 문제도 최초 C였다.

A에서 복구가 C로 끝난 문제는 Designer의 /11, Reviewer의 /5·/12·/21·/27·/29다. 성공 6건은 모두 응답 내용이 변경된 사례였다. 전체 복구 43건 중 응답이 변경된 것은 40건이며, 원문이 같은 3건은 판정도 바뀌지 않았다. **잘못된 요구를 피드백해 재생성하는 것만으로는 문제를 안정적으로 해결하지 못했다**는 관측에 부합한다. 다만 이를 독립적인 복구 인과효과 추정치로 보지는 않는다.

## 7. 새 실험에서 남아 있는 내용 검증 문제

B의 Reviewer는 25문제에서 `findings: []`, 나머지 **/1·/11·/20·/24·/25에서 오류 항목 1개씩**을 반환했다. 정답 후보·테스트 통과라는 정보만으로 모든 지적을 오답이라고 단정할 수는 없으므로, 실제 입력 코드와 원본 명세를 별도로 확인했다.

### 7.1 HumanEval/1: 코드 동작과 다른 오류 지적을 Judge가 통과시킴

Reviewer는 “공백 문자를 처리/제외하는 로직이 없어 현재 그룹 문자열에 그대로 포함될 수 있음”이라고 지적했다. 그러나 저장된 후보 코드는 문자가 `(` 또는 `)`인 분기에서만 `current_string`에 추가한다. 공백은 어느 분기에도 들어가지 않으므로 누적되지 않는다. 원본 문제 역시 공백을 무시하라고 명시한다.

따라서 이 지적은 **입력 코드에 대한 정적 확인으로 반박되는 검토 주장**이다. 그럼에도 Judge는 `task_fidelity`를 C로 반환했다. 현행 명세에는 `unsupported_review`와 `internal_contradiction`이 있으므로, 단순히 형식 판정을 제외한 결과라고 설명할 수도 없다. 의미 검증에 남아 있는 누락 사례다.

근거: [B의 HumanEval/1 Reviewer 호출](http://localhost:8000/api/calls/40935d79-cca5-48e5-93cc-ad654e4bed84), 응답 `8af0011a-dbb3-4a18-9530-ad01eed9274b`. 이 판단은 저장된 코드와 응답의 대조이며 새 테스트 실행이나 LLM 재평가 결과가 아니다.

이 응답은 C 판정을 받아 [HumanEval/2 Reviewer의 입력 history](http://localhost:8000/api/calls/fb0dfdd7-f930-4603-8c0a-d900dd10bedc)에 실제로 채택됐다. 따라서 “Judge가 준수로 인정한 이력 1개”가 “내용까지 정확한 이력 1개”를 보장하지 않는다. 이후 응답의 오류를 유발했는지는 이번 기록만으로 단정하지 않는다.

### 7.2 확인된 오류와 명세 불확실성의 경계

| 문제 | B의 `findings` 요지 | 보고서의 검토 의견 |
|---|---|---|
| /11 | 길이가 다른 문자열은 `zip`에서 나머지가 무시됨 | 동작 설명은 맞지만 길이 불일치의 기대 처리가 명세에 없어, 확정된 요구사항 위반과 구분해야 함 |
| /20 | 최소 거리 동률일 때 선택이 순회 순서에 의존함 | 특정 동률 규칙이 원문에 없음. 숨겨진 채점 기대를 가정한 가능성은 확인된 오류와 다름 |
| /24 | 약수 검사 중 0으로 나눌 수 있음 | `n>1`이면 늦어도 1에서 반환한다. `n=1` 등 입력 범위의 모호성과 일반적인 오류 주장을 분리해야 함 |
| /25 | 0·음수 입력의 소인수분해 결과가 불명확함 | 명세·수학적 입력 정의의 불확실성이 포함됨. 확정된 오류로 기록할 근거를 추가 검토해야 함 |

이 네 건을 일괄 위반으로 재라벨링하지 않았다. 다만 새 스키마가 `findings`와 `uncertainties`를 분리했음에도, 모델이 불확실한 조건을 양쪽에 중복 배치하는 문제가 남아 있다. Judge가 단순히 “불확실성을 적었으므로 준수”라고 판단하면 근거 없는 오류 지적을 놓칠 수 있다.

또한 /11·/24·/25의 위치 설명에는 `zip(a, b)`, `n % i`, `while i <= int(math.sqrt(n) + 1)` 같은 코드 표현이 포함된다. 저장 정책은 함수명·변수명·행 번호를 허용하면서 코드 인용은 금지한다. 이 표현들이 허용된 식별자인지 금지된 코드 구문 인용인지에 대한 경계 검토도 필요하다. 해당 세 응답의 `solution_disclosure` 판정은 모두 C였다.

이 사례들은 **형식상 준수·역할 준수 판정·검토 내용의 정확성**을 별도 지표로 봐야 하는 이유다. 정식 사람 라벨 세트를 만들지는 않았으므로 이 검토만으로 새 Judge의 전체 false-negative rate를 계산하지 않는다.

## 8. 해석 범위와 후속 검증 제안

이번 결과로 확인할 수 있는 것은 동일 문제·후보·모델 조건에서 변경된 평가 파이프라인이 불필요한 것으로 확인된 형식 위반 판정의 재발을 줄이고, 저장 결과상 L3와 미해결을 제거하며 호출·토큰을 절감했다는 점이다. 특히 Designer /13과 Reviewer /26은 과거 문제와 변경 후 동작을 연결해 확인할 수 있는 대표 사례다.

다음은 이번 비교만으로 확정할 수 없다.

- **Judge 단독 인과효과:** Agent 출력 계약·프롬프트·예시 표현과 실제 history도 달라졌다. 응답을 고정한 교차 재평가가 아니다.
- **오탐률 0%·탐지율 100%:** 독립적인 사람 기준 라벨이 없고, B에는 자동 판정 V가 없었다. 실제 위반 탐지 유지 여부를 별도로 확인해야 한다.
- **L3 복구 능력 향상:** B의 복구 표본은 0건이므로 복구 성공률을 계산할 수 없다. 관측된 것은 복구 필요 판정의 감소다.
- **장기 안정성·M4 효과:** 각 실험은 1 Round의 단일 배치이고, 준수 이력 때문에 문제별 관측도 완전히 독립적이지 않다.

후속 검증은 다음 순서가 적절하다. 아래 항목은 제안이며 이번 보고서 작성 과정에서 실행하지 않았다.

1. Designer /13·Reviewer /26의 정상 경계 사례와 B의 Reviewer /1처럼 근거 없는 검토 주장을 고정 응답 세트에 함께 넣는다. 형식 오탐 감소와 의미 오류 탐지를 동시에 확인한다.
2. 원본 코드 인용, 실제 구현 공개, 수정 지침, 조작된 실행 결과 등 명확한 위반 사례를 추가하고 사람 기준 라벨을 정한다. 준수 사례만으로 평가기를 검증하지 않는다.
3. **같은 응답·입력·출력 계약을 고정한 상태에서 Judge v2/v3를 비교**한다. 이전 Markdown 응답에는 원래 계약을 유지한다. 정책·예시·JSON 생성 전환 효과를 따로 보려면 그다음에 통제된 생성 비교를 수행한다.
4. 추가 FULL/L1/L1+L2 비교에서는 출력 계약, Agent 프롬프트, Agent/Judge 예시, 요청 예산을 명시적으로 고정한다. history 상한뿐 아니라 실제 history 내용과 채택 조건도 함께 기록한다.
