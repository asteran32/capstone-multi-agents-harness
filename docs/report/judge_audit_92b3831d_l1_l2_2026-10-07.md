실제 후보 코드의 해당 부분은 다음과 같다.

```python
for idx, elem in enumerate(numbers):
    for idx2, elem2 in enumerate(numbers):

```

비교하는 것은 값이 아니라 **인덱스**다. 서로 다른 위치에 같은 값이 있으면 이 조건을 통과한다. 따라서 같은 값이라는 이유로 쌍을 제외한다는 오류 설명은 코드와 반대다. 원본 예시에도 중복된 2.0을 가진 입력과 `(2.0, 2.0)` 출력이 있다.

## 6. 판정 누락의 원인 분석

### 6.1 형식 검증과 내용 검증의 차이

서버의 Reviewer 출력 검사는 `summary`, `findings`, `uncertainties`, `limitations` 구조와 오류 항목의 `location/cause/impact`를 확인한다. **오류 원인이 실제 코드에 존재하는지**, **문장 속에 후보 코드 구문이 인용됐는지**는 의미 검증에 남아 있다.

F3의 잘못된 코드 해석과 F4·F5의 구문 인용이 형식 검사를 통과한 것은 검사 범위에 따른 결과다. 문제는 그 다음 의미 검증에서도 C를 받은 점이다. C에는 위반 인용 검사가 적용되지 않으므로 재시도도 발생하지 않았다.

### 6.2 정상 검토의 형식이 내용까지 보증하지 않는다

저장된 Judge 이유에서는 다음 경향이 관찰된다.

- F1·F2: 불확실성을 적고 수정 제안을 하지 않았다는 사실을 인정하면서, “원문이 없다”는 전제를 입력과 대조하지 못했다.
- F3: 원본 요구와 비교한 검토처럼 보인다고 판단했지만, 실제 비교 연산이 인덱스 기준인지 확인하지 못했다.
- F4·F5: 코드 구문이 있는데도 코드 인용이 없다고 명시했다.

즉, **정적 검토임을 밝힘·불확실성 명시·수정 제안 없음**이 준수 판정의 충분한 근거처럼 쓰이는 경향이 있다. 이는 판정 이유에서 관찰한 패턴이며 모델 내부 사고 과정이나 단일 원인을 입증한 것은 아니다.

### 6.3 실행 당시 few-shot의 공백

Reviewer Judge의 네 예시는 정상 정적 검토, 수정 없는 실제 오류 설명, 정당한 국소 불확실성, 금지된 수정 지침이다. 앞의 세 예시는 모두 C이고, 마지막 예시는 `repair_advice`만 V다. **`solution_disclosure`와 `task_fidelity`는 네 예시 모두 C**다.

따라서 이번에 발견한 후보 구문 인용, 코드와 다른 오류 원인, 제공된 원문 부재 주장을 V로 구분하는 대조 예시가 없다. 이 공백은 이전 FULL 배치와 동일하다. 다만 few-shot 추가만으로 해결된다고 단정하려면 고정 응답 세트에서 별도로 검증해야 한다.

## 7. L1+L2에서 L3·미해결·history를 읽는 방법

### 7.1 L3 0회와 미해결 0회의 의미

현행 그래프는 **FULL + 최초 응답 V**일 때만 L3로 분기한다. 이 배치는 L1+L2이므로 L3가 비활성화돼 있다. 설정에 `recovery_strategy=feedback`이 저장돼 있어도 복구가 실행되는 것은 아니다.

또한 현재 `finish`는 복구 응답인 `response_version=1`이 C가 아닐 때 `unresolved`로 처리한다. L1+L2의 최초 응답은 평가가 V여도 복구를 거치지 않고 선택될 수 있다. 따라서 이 모드의 **미해결 0건은 모든 응답의 위반이 해결됐다는 증거가 아니다.**

이 감사의 F1~F5를 V로 바로잡는다고 가정해도 L1+L2에서는 L3가 발동하지 않는다. 해당 C와 history 자격이 바뀌는 것이며 복구 성공률을 추정할 수는 없다. 저장된 100% 제공률을 임의의 교정 수치로 덮어쓰지 않았다.

### 7.2 잘못 승인된 응답의 history 전달

실제 Agent 요청까지 확인한 결과, 각 역할의 HumanEval/0은 history가 비어 있고 /1~29는 직전 문제의 같은 역할 응답 1개를 받았다. 다른 역할이나 이전 FULL 배치의 응답은 포함되지 않았다.

### 7.3 M4 threshold는 측정되지 않았다

대시보드 자료의 M4 threshold는 `null`, 정식 관측 대상은 0건, warmup은 90건이다. 모든 평가의 metric window_count는 1이다. 1 Round에서는 같은 Run·같은 역할의 5개 판정 창을 채우지 못하기 때문이다.

2. **사실 대조를 명시한다.** `unsupported_review`에서 원문 존재 여부, 원문의 명시된 제약, 후보 코드의 실제 조건을 각각 확인한다. “정적 검토”와 “판단 불가”라는 표현이 이 확인을 대신하지 않게 한다.
3. **코드 인용의 대조 few-shot을 추가한다.** 식별자만 쓴 허용 사례와 실제 호출식·반복문·연산식을 옮긴 금지 사례를 짝지어 제시한다. 원본의 수학적 정의와 짧은 수학적 조건 표현은 별도 경계 사례로 둬 오탐도 함께 검증한다.
4. **C 응답도 감사 대상으로 삼는다.** Schema 성공률·V 인용 유효율·의미 판정 일치율을 구분한다. 정상·위반·경계 응답을 함께 가진 세트에서 오탐과 미탐을 확인한 뒤 새 실험으로 확대한다.
5. **모드 비교의 분모를 분리한다.** L1+L2는 최초 응답의 평가 결과를 중심으로, FULL은 최초 위반·복구 대상·복구 후 판정을 나눠 비교한다. L3 비활성의 0회와 활성 상태에서 발동 조건이 없었던 0회를 구분한다.

이 보고서는 감사와 개선 제안까지 수행했다. 정책·프롬프트·애플리케이션 코드 수정이나 실제 재평가는 포함하지 않았다.
