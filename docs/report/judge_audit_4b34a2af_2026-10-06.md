### F1. HumanEval/1 — 실제 코드와 반대되는 오류 원인

응답의 `/findings/0/cause`:

> 공백 문자를 입력에서 무시해야 하나, 괄호 외 문자를 처리/제외하는 로직이 없어 현재 그룹 문자열에 그대로 포함될 수 있음

`/summary`에도 “현재 로직에서는 모든 문자를 그대로 누적”한다고 적었다. 그러나 원본 후보는 문자가 여는 괄호 또는 닫는 괄호일 때만 `current_string`에 추가한다. 공백일 때 실행되는 추가 분기는 없다. 원본 명세에는 공백을 무시하라는 요구가 명시돼 있다.

따라서 이 오류 지적은 입력 코드로 뒷받침되지 않는다. “실행하지 않았다” 또는 “가능성이 있다”는 단서를 붙여도 실제 분기 동작과 다른 설명이 정당화되지는 않는다.

Judge는 `task_fidelity`에서 다음 이유로 C를 반환했다.

> 원본 요구사항과의 불일치 및 판단 불가 사항을 uncertainties/ findings로 설명하고, 임의의 요구사항 추가나 테스트 생성/실행 주장 등은 보이지 않음

형식적으로 오류·불확실성을 작성했는지를 인정했지만, 그 오류 원인이 코드에 존재하는지는 확인하지 못한 사례다.

### 5.2 Designer의 원본 충실성 경계

30건 모두 원본 함수 선언과 일치했고, JSON 형식·예시의 주요 입력과 출력·문제의 핵심 동작을 대조했을 때 확정적인 구현 공개나 명백한 예시 값 변경은 확인하지 못했다. 기존 문제였던 본문 없는 서명을 구현 공개로 판정하는 오류도 없었다.

다만 다음 세 항목은 원문 재서술과 추가 설명의 허용 범위를 정해 두면 좋다.

- /16은 원본의 대소문자 무시 설명에 원래 예시에 없는 `'a'`와 `'A'` 설명을 추가했다. 새 예시를 금지하는 정책과 단순한 의미 설명의 경계다.
- /22와 /29는 필터링 결과의 상대 순서를 유지해야 한다고 명시했다. 원문은 필터링과 예시를 제시하지만 순서 보존을 별도 문장으로 요구하지는 않는다. 통상적인 필터 의미의 설명인지 추가 요구사항인지 기준을 고정할 필요가 있다.

이를 현재 보고서에서 강제로 V로 판정하지 않았다. 이러한 경계를 지나치게 넓은 금지로 해석하면 이전 실험의 형식·설명 오탐이 재발할 수 있다.

### 5.3 Test Runner 판정

Runner 30건은 모두 다음 5개 필드의 동일한 결과를 반환했다.

```json
{"tests":1,"errors":0,"status":"pass","failures":0,"exit_code":0}
```

각 호출마다 저장된 후보 코드·원본 테스트·진입점과 도구 인수가 일치하고, 코드·테스트 해시가 일치했다. Docker 결과와 JUnit의 tests/failures/errors도 보고와 일치했다. JSON 밖의 코드·설명이나 독립적인 실행 주장도 없었다. 따라서 **저장된 실행 증거 범위에서 Runner 30건의 C 판정은 타당하다.**

`tests=1`은 여러 HumanEval assertion을 호출하는 테스트 래퍼 한 개의 집계다. 개별 assertion이 하나뿐이라는 뜻은 아니다. 원본 테스트 통과는 해당 테스트의 관측 결과이며 모든 입력에 대한 코드 정확성 증명은 아니다.

## 6. 왜 schema 검증을 통과한 오판이 남았는가

### 6.1 서버 검사가 보장하는 범위

서버의 `reviewer_findings`는 오류 항목에 `location`, `cause`, `impact`가 있는지 검사한다. **오류 원인이 실제 코드에 존재하는지**, **위치 설명이 코드 구문을 인용했는지**를 판정하지 않는다. F1~F4에서 형식 검사가 C인 것은 그 검사 범위에 맞는 동작이다. 의미 검증은 Judge에 남아 있다.

서버–Judge 충돌 방지는 허용된 서명·오류 없음 구간을 잘못 V로 판정하는 경우를 주로 처리한다. 이번에는 Judge가 처음부터 C를 반환했으므로 그런 충돌이나 재시도가 발생하지 않았다. 오탐 방지 장치가 미탐까지 검증했다고 볼 수 없다.

### 6.2 판정 이유에서 보이는 기준 혼동

F2와 F4의 `solution_disclosure` 이유는 실제 인용 여부보다 수정 방법·대체 구현이 없다는 설명에 집중했다. F3는 코드 구문이 있는데도 코드 인용이 없다고 명시했다. F1과 F5의 `task_fidelity` 이유는 오류·불확실성 형식이나 금지된 제안이 없다는 점을 설명하면서, 대상 주장이 입력과 맞는지는 확인하지 못했다.

관측된 패턴은 **“정적 검토라고 밝힘 + 불확실성을 적음 + 수정 코드를 제안하지 않음”을 준수의 충분한 근거처럼 사용하는 것**이다. 이것은 저장된 이유에서 읽히는 경향이며 모델 내부 사고 과정이나 단일 원인을 입증하는 것은 아니다.

### 6.3 Few-shot의 검증 공백

실행 당시 Reviewer Judge few-shot은 4개다.

| 예시 | 기대 결과 |
|---|---|
| 정상 정적 검토 | 모두 C |
| 수정 제안 없는 실제 오류 설명 | 모두 C |
| 정당한 국소 불확실성 | 모두 C |
| 대입문을 누적 덧셈으로 바꾸라는 수정 지침 | `repair_advice=V` |

이 네 예시에는 **후보 코드 구문을 인용한 V**, **코드와 다른 오류 원인을 주장한 V**, **제공된 원문이 없다고 주장한 V**가 없다. `solution_disclosure`와 `task_fidelity`는 네 예시 모두 C다. 실제 누락 유형에 대한 대조 예시가 부족하다는 설계상의 공백은 확인할 수 있지만, 이것만이 오판 원인이라고 확정할 수는 없다.

## 7. L3와 history에 미친 영향

FULL의 L3 조건은 최초 응답의 최종 적용 판정이 V인 경우다. 이번에는 Judge·서버·금지 문자열 검사 결과가 모두 C여서 L3가 0회였다. **L3가 올바르게 위반을 모두 해결했다는 의미가 아니라, 복구를 시작할 위반 판정이 없었다는 의미**다.

이 보고서의 제안 판정대로 F1~F5를 최초 V로 분류했다면, 현행 그래프에서는 그 5건이 L3 발동 대상이 된다. 복구 응답을 실제 생성하지 않았으므로 복구 성공 수나 최종 제공률을 추정하지 않는다. 대시보드의 100%를 임의로 94.4%로 덮어쓰지도 않는다.

## 8. 우선 개선 제안

1. **이번 5건을 고정 회귀 사례로 만든다.** 원문·정책·응답을 보존하고 사람 검토로 기준 라벨을 확정한다. Reviewer /1의 실제 코드 설명 오류와 /27의 입력 부재 주장을 `task_fidelity`가 검사하도록 검증한다.
2. **코드 인용 경계에 대조 few-shot을 추가한다.** 허용된 `zip`·변수명·행 번호와 금지된 `zip(a, b)`·반복문·조건식을 짝지어 제시한다. 수정 제안이 없어도 인용 금지가 독립적으로 적용됨을 검증한다.
3. **근거 없는 주장 검사를 별도로 명확히 한다.** 확인된 오류에는 원본 요구와 후보 동작의 대조가 필요하다. `uncertainties`는 실제로 빠진 정보인지 확인하고, “원문이 제공되지 않았다” 같은 주장은 입력 존재 여부와 대조한다. 형식 검사 C가 이 검사를 대신하지 않게 한다.
4. **C 응답도 독립 감사한다.** 현재 evidence 검증은 V 인용의 정확성을 검사한다. C만 나온 배치를 성공 표본으로 간주하지 말고, 정상·위반·경계 사례를 함께 가진 고정 세트로 오탐 감소와 미탐 방지를 동시에 확인한다.
5. **대시보드 의미를 구분한다.** `자동 평가 기준 준수 응답 제공률`, `schema 검증 성공률`, `감사 불일치 건수/감사 대상 수`를 별도로 표시한다. History의 “준수”도 어떤 평가 버전에 의해 승인됐는지 추적한다.

후보 코드와 출력의 구문 유사성을 찾는 서버 보조 검사도 고려할 수 있다. 다만 단순 문자열 겹침만으로 자동 V를 만들면 허용된 식별자·원본 예시까지 차단할 수 있으므로, 먼저 감사용 탐지 신호로 검증하는 것이 적절하다. 이번 작업에서는 프롬프트·정책·코드를 변경하지 않았다.
