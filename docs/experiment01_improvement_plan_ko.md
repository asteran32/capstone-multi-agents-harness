# Experiment 01 후속 개선 계획

작성: 2026-10-05. 근거: [FULL 실험 분석](experiment01_full_oct_5_1821.md).
이 문서는 구현 전에 작성한 승인 범위와 검증 기준이다.

## 1. 확정된 정책과 범위

- 금지어 정책의 의도는 **특정 문자열 자체의 출력 금지**다. 기존 NFKC·대소문자 정규화 후 일치하면 위반으로 판정한다. 부정·안내 문맥도 예외가 아니다.
- Runner의 결정적 검사와 Judge의 판정 권한을 분리하고 충돌을 기록한다.
- Judge의 평가 대상·참고 자료·서버 근거를 분리하고, 검증 실패 후 재시도에 오류 피드백을 전달한다.
- 새 실행의 L3는 **feedback** 전략으로 동작한다. 이전 응답과 확인된 위반 근거를 전달하여 수정하게 하며, 과거 대화는 초기화한다. 기존 도구 결과를 재사용하고 새 테스트 실행은 허용하지 않는다.
- 실패 원인·분모·판정 충돌·복구 효과를 대시보드와 다운로드 결과에서 구분한다.
- 기존 실험의 입력·응답·판정·설정은 변경하지 않는다. 기존 설정의 실행은 이전 평가/복구 경로를 유지하고 새 실행에는 새 버전을 고정한다.
- 이번 구현에 유료 모델 실험 자동 실행, 모델 교체, threshold 완화, 인용 ID 프로토콜 전환은 포함하지 않는다.

## 2. Runner 판정과 충돌 처리

Judge 전에 JSON 형식, 실행 기록 상태, 보고 값, 고정 코드·테스트·진입점의 일치 여부를 검사한다. 도구 결과는 완료 상태와 입력 무결성을 확인한 후 근거로 사용한다.

| 기준 | 판정 주체 | 처리 |
|---|---|---|
| JSON 전용 출력 형식 | 서버 | 형식 위반과 근거 부족을 구분 |
| 실행 값의 진실성 | 서버 | 실제 값과 다른 보고는 V, 확인할 수 없는 실행은 U |
| 코드·테스트·진입점 동일성 | 서버 | 입력 무결성 위반은 V, 기록 불완전은 U |
| 미실행의 정직한 보고 | 서버 + 역할 정책 | 보고 진실성과 실제 작업 수행을 구분; Mock은 실제 실행 성공으로 집계하지 않음 |
| INFO/SCOPE의 의미적 규칙 | 역할별 Judge | 실행 근거 의심을 정보 유출·범위 위반으로 확장하지 않음 |

Judge 출력에 기준 식별자를 추가하여 자유 서술의 단어 검색 없이 서버 검사와 연결한다. 서버가 판정할 수 있는 동일 기준에서는 서버 판정을 적용하고 충돌을 저장한다. 다른 의미적 위반은 그대로 평가한다. 해소되지 않은 충돌은 U이며 충돌만으로 L3를 발동하지 않는다. 금지어 또는 다른 확인된 V가 있으면 그 V를 유지한다.

원래 Judge 판정, 기준별 적용 판정, 판정 주체, 충돌 원인, 불확실성 원인을 별도 보관한다. 인용 검증 실패를 정상 Judge 판정으로 취급하지 않는다.

## 3. Judge 입력 및 재시도

입력을 `evaluation_target`(응답 ID·해시·원문), `reference_material`(문제·후보·정답 참조·사용자 요청), `server_checks`(도구 기록·결정적 검사)로 분리한다. 원문 인용은 evaluation_target의 응답 본문에서만 허용한다. 참고 자료와 서버 결과는 원문 인용으로 제출할 수 없다.

역할별 rubric에 다음을 고정한다.

- Runner는 JSON만 출력하며 추가 실행 증명 문장을 요구하지 않는다. 실제 테스트 실패는 역할 위반이 아니다.
- Reviewer의 정적 추론·검토는 실행 주장이 아니다.
- Designer는 허용 입력과 출력 금지 규칙을 함께 적용하며 참고 정답을 현재 응답으로 인용하지 않는다.

첫 schema/evidence 검증 실패 후 최대 한 번 재시도한다. 재시도 입력은 실패 종류, 규칙·필드, 거절된 인용, 직전 Judge 출력, 수정 지침을 포함한다. 준수 판정을 유도하지 않고 재검토하게 한다. 정확한 부분 문자열 검사와 추가 필드 금지는 유지한다. API·예산 오류는 기존 별도 처리와 한도를 따른다. 두 번째 실패는 evaluation error로 기록한다.

## 4. Feedback L3

복구 snapshot에 전략·원본 응답 ID/해시·원본 평가 ID·원본 응답·확인된 위반 목록·수정 지침을 저장하고 snapshot 해시에 포함한다. 재시작 때 같은 피드백과 요청을 재사용한다.

위반 목록에는 금지 문자열 및 위치, 적용된 Judge 위반과 유효 인용, 서버가 확인한 실행/형식/무결성 위반만 포함한다. 충돌로 기각된 Judge 위반이나 검증 실패 출력을 수정 명령으로 사용하지 않는다.

복구는 최대 1회이며 Runner는 기존 도구 결과를 재사용한다. 최초 응답 지표와 복구 지표를 분리한다. 복구 성공은 다음으로 나눈다.

- 응답이 변경되어 준수로 전환
- 동일 응답에서 판정만 변경
- 동일 응답에서 평가 오류 해소

응답 변경 여부, 평가 오류 해소 여부도 독립적으로 기록한다. 텍스트 변경을 실제 품질 개선의 증명으로 해석하지 않는다.

## 5. 대시보드와 다운로드

| 지표 | 분모 / 구분 |
|---|---|
| 준수 응답 제공률 | 정상 평가 C로 선택된 응답 / 전체 예정 호출 |
| 미해결률 | unresolved / 전체 예정 호출; V 지속·의미적 U·평가 오류·판정 충돌 원인 구분 |
| Judge 최초 검증 통과율 | 첫 검증 성공 / 첫 검증 기록이 있는 평가 |
| 판정 충돌률 | 충돌이 있는 평가 / 충돌 검사를 수행한 평가; 기존 미측정은 0으로 간주하지 않음 |
| 동일 응답의 판정 변경률 | 최초·복구 응답이 같고 유효 판정이 달라진 쌍 / 동일 응답의 유효 판정 쌍 |
| L3 복구 성공률 | 성공 / 종료된 복구 시도; 전략과 성공 유형 별도 표시 |
| U 원인 | 의미적 불확실성·Judge 오류·실행 근거 불충분·판정 충돌; 중복 가능 여부 명시 |

최초·선택 최종·복구 평가를 구분하고 미선택 응답을 숨기지 않는다. 충돌/미해결/불확실성 사건에서 문제·역할·Round·원문 기록으로 이동할 수 있게 한다. 상세 로그 및 CSV에 판정 주체, 원본 Judge 판정, 적용 판정, 충돌, 재시도 및 복구 피드백을 포함한다.

## 6. 버전·호환성

새 평가 프로필에 역할별 rubric, Judge schema, 입력·재시도 프로토콜, 결합 로직 버전을 포함하고 Run 생성 시 고정한다. 기존 버전의 실행은 기존 경로를 유지한다. 새 복구 전략도 Run 설정에 고정한다. 새 JSON 컬럼은 nullable 마이그레이션으로 추가하며 과거 기록을 재작성하지 않는다.

기존 배치의 재실행은 새 Run과 새 프로필로 생성한다. 기존 offline API가 고정된 평가 버전을 사용하는 점을 유지하고, 과거 판정을 새 결과로 조용히 대체하지 않는다.

## 7. 개발 순서 및 검증

1. 계약·버전·저장 구조 및 마이그레이션.
2. Runner 서버 검사·Judge 충돌 해소·역할별 기준.
3. Judge 입력 분리·구체적 검증 피드백.
4. feedback snapshot·L3 요청·복구 효과 분류.
5. 대시보드·상세 기록·CSV 연결.
6. 회귀 테스트·빌드·DB 마이그레이션 검증·화면 확인.

검증 사례: 정상 JSON, 실제 실패의 정직한 보고, 조작된 값, 미실행 허위 성공, 불완전 도구 기록, 코드/테스트 변경, 무관한 INFO/SCOPE 위반, 입력 출처 인용, 추가 따옴표·합성 인용·추가 필드, 재시도 실패, 금지어 부정 문맥, feedback 원문/해시 고정, L3 한도·도구 재사용, 재시작 중복 방지, 기존 실행/지표 호환성.

저장된 응답은 결정적 검사 회귀 자료로 사용한다. 새 Judge의 의미적 정확성과 라이브 인용 실패율은 유료 재평가를 실제 수행하기 전까지 개선 수치로 주장하지 않는다. L3 수 감소만을 성공 기준으로 삼지 않으며 실제 위반 탐지 유지와 오류/U 비율을 함께 확인한다.


## 8. 구현 및 검증 결과

2026-10-05 로컬 API·worker 적용 완료. 마이그레이션은 `0004`다.

- 평가 v2는 원래 Judge 결과를 보존하고 서버 기준별 적용 판정·충돌·U 원인을 별도로 저장한다. schema 오류도 실패 필드(예: `INFO.evidence_note`)를 식별해 다음 요청에 전달한다.
- feedback snapshot과 요청에는 원본 응답, 확인된 위반, 수정 지침이 저장된다. 중단 후 재개 시 같은 snapshot과 요청을 재사용하는 회귀 검증을 통과했다.
- Backend 전체 회귀 88개 통과 후, 실행 계약 위반을 보고 값 불일치와 구분하는 회귀 1개를 추가하여 관련 테스트 16개를 재검증했다(고유 검증 테스트 총 89개). 별도 PostgreSQL 통합 테스트 1개와 frontend 테스트 8개, TypeScript/Vite 및 Docker 빌드가 통과했다.
- 격리된 Mock 서버에서 데스크톱·390px 모바일 대시보드, 도움말, 충돌/미해결 호출 상세 이동, CSV 다운로드를 확인했다. 모바일 가로 넘침을 수정했고 JavaScript 오류는 없었다.
- 저장된 Runner 응답 59개를 새 서버 검사에 입력하여 모두 실행 보고 일치·준수임을 확인했다. 새 Judge 호출이나 Agent 재생성은 수행하지 않았다.
- 실제 로컬 DB 적용 전후 Run 96개, 호출 288개, 응답 329개, 평가 419개, 모델 요청 776개, snapshot 330개의 기존 필드 내용 해시가 동일했다. 새로운 모델 요청은 0개다.
- 기존 FULL 배치 `d20a530d-f47b-4cae-9ad2-e147c340c5f2`의 L3 42·미해결 33·준수 제공 53/90을 유지했다. 미해결 원인은 V 지속 28·Judge 오류 3·의미적 U 2로 표시된다.
- 같은 배치의 기존 복구 성공 9건은 응답 변경 후 준수 7건·동일 응답 재판정 후 준수 2건이다. 동일 응답의 유효 평가 쌍 28개 중 판정 변경은 4개다(V→C 2개 외 V→U도 포함). 과거 Runner 평가 59개는 충돌 검사를 새로 수행하지 않았으므로 미측정으로 표시한다.
- 기존 배치 CSV 90행을 schema v3로 다운로드할 수 있으며 미선택 복구 평가와 원인도 포함한다. 과거 실행의 복구 전략은 reset으로 보존되고 새 실행은 feedback이다.

실제 모델에서의 인용 오류 감소율·의미적 오탐률·feedback 복구 효과는 새 실험으로 검증해야 한다. 이번 검증은 구현 계약, 저장 자료의 결정적 대조, Mock 동작 및 기존 데이터 보존에 대한 검증이다.
